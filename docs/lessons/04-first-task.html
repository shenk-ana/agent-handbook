第一次委托任务
从“提示词”到“任务简报”

你跟新来的同事说“帮我弄一下周末的事”，他多半会一脸茫然。跟 Claude 说话也一样。它很能干，但它不知道你脑子里的那些条件。多花一分钟把事情交代清楚，往往能省下好几轮返工。

⏱ 约 15 分钟 👤 所有人；原理层面向开发者 🎬 2 个交互演示 · 1 个简报生成器

学完这一课，你能

  • 说出模糊指令为什么会导致来回返工
  • 用六个部分写出一份任务简报
  • 让 Claude 在动手之前先问清楚
  • 在任务进行中看过程、及时纠偏，并按完成标准验收
  • （开发者）在 Claude Code 里写出可验证的完成标准，并用计划模式先对齐方案

一句话总结

把“一句话指令”换成“一份简报”：目标、背景、限制、交付形式、完成标准，再加一句“有不清楚的先问我”。

01同一件事，两种交代方式

02一份简报的六个部分

写给 Agent 的完整说明，本书叫它任务简报。它通常包括六个部分：

部分回答的问题演示里的例子
① 目标你最终想要什么结果？周六下午带孩子出去玩 3 小时左右
② 背景它需要知道哪些你知道、它不知道的事？孩子 5 岁，住东区，没有车，周六有雨
③ 限制哪些条件必须遵守、哪些事不许做？地铁单程 40 分钟内，总预算 200 元；不要推荐需要开车的地方
④ 交付结果做成什么样子？3 个选项，做成表格，列交通、费用、理由
⑤ 完成标准怎样才算做完、做对？每个选项都核对过开放时间，附来源
⑥ 先问我信息不够时怎么办？有不清楚的先问我
🧩
打个比方：给聪明的新同事派活

Anthropic 官方的建议是，把 Claude 想象成一位非常聪明、但刚入职的新同事：他能力很强，却不了解你的习惯和背景。还有一个简单的检验办法：把你写的话拿给一位不了解情况的同事看，如果他会困惑，Claude 多半也会。

几个写简报的小技巧：

  • 说出“为什么”。“要室内的，因为周六下雨”比“要室内的”更好。知道原因，Claude 能举一反三，比如自动排除露天的游乐场。
  • 完成标准要能检查。“做得好一点”没法检查；“每个选项都附上来源”可以检查。可检查的标准，Claude 自己也能判断做没做完。
  • 不必每栏都写满。简单的事一两句就够了。目标一定要有，其他几栏按需要补。
  • 给例子。想要某种格式或语气，直接贴一段你喜欢的样例，比描述半天更准。

03让它先问问题

简报里最省事的一句话是：“有不清楚的先问我。”演示 B 里，Claude 只问了一个问题“孩子更喜欢动手玩还是看展”，你只回答了几个字，结果就准了很多。

这句话的作用，是给 Claude 一个“不必硬猜”的出口。没有它，Claude 通常会按最常见的情况先做一版。有了它，遇到会影响结果的空白时，它会先停下来问你。你还可以限定数量，比如“最多问三个问题”，免得它问个没完。

反过来，如果你赶时间，也可以明确说：“不用问我，按你的判断做，把你做的假设列在最后。”这样你至少知道它在哪里猜了。

05交出去以后：看、纠、验

简报发出去，事情还没完。和 Agent 合作的后半程有三件事：

  1. 看过程：留意它搜了什么、读了什么。界面上的“正在搜索……”和来源列表，就是它的工作记录。
  2. 及时纠偏：发现方向不对，不必等它做完。直接补一句“等一下，我们没有车”，它会调整。越早纠正，浪费越少。
  3. 按标准验收：拿你写的完成标准对一遍。说好附来源的，点开一两个看看；说好控制预算的，加一加总数。

同一类事情要反复交代时，把简报存下来，下次改几个字就能用。经常用的固定要求，可以写进 Projects 的项目说明（第 5 课），或者做成 Skill：一份打包好的“做事说明书”，Claude 接到对应的活儿时会自动拿出来照着做（第 7 课）。

原理层在 Claude Code 里写任务简报▾

开发场景的简报结构一样，但有两个特别有用的做法：

  • 完成标准写成命令：例如“完成标准：npm test 和 npm run lint 全部通过；不修改 src/legacy/ 下的文件”。Claude Code 能自己运行这些命令来判断是否完成，这正是第 15 课演示里“改完再跑一遍测试”的来源。
  • 先对齐方案再动手：较大的改动先用计划模式（/plan）让它只出方案、不改文件，你确认后再执行。这相当于简报里的“先问我”，只是对象从信息变成了方案。

还要分清两种信息的去处：

信息放在哪
本次任务的目标、限制、完成标准当次的提示词（任务简报）
每次都适用的约定：测试命令、代码风格、禁区目录项目的 CLAUDE.md（第 12 课）
反复执行的固定流程，例如“发版前检查”Skills 或自定义命令（第 13 课）

Anthropic 的提示词最佳实践还强调：想让它做得比字面要求更多（例如“尽量完善”），要明确说出来，不要指望它从模糊的指令里推断；需要按顺序执行的步骤，用编号列表写清楚。

06动手试一试

✍️ 把一句话改写成简报 不需要写代码
  1. 想一件你最近真想交给 AI 的事，先只用一句话交代，看看结果。
  2. 用第 04 节的生成器补全六个部分，在新对话里再交代一次。
  3. 对比两次：第二次它问了你什么问题？结果更接近你要的吗？

也可以让 Claude 帮你把简报写完整：

我想请你帮我做一件事：（一句话描述）。先别开始做。请帮我把它整理成一份任务简报，包括目标、背景、限制、交付形式和完成标准。缺的信息请逐条问我。
🖥 给 Claude Code 一份带验收标准的简报 开发者 · 需要电脑操作
目标：给 utils/date.js 里的 formatDate 增加对时区参数的支持。背景：前端会传入 IANA 时区名，例如 Asia/Tokyo。限制：不引入新的依赖，不改动现有函数签名的默认行为。交付：代码改动加对应的单元测试。完成标准：npm test 全部通过。开始改代码之前，先给我一个简短的方案，等我确认。

  2. 观察它是否先给方案、等你确认；完成后是否主动运行了测试。

07常见误区

✗

写提示词有秘诀，网上抄一段“万能咒语”就行。

✓

对当前的 Claude 来说，把事情交代清楚，比找“万能咒语”有用得多。你知道而它不知道的信息，才是关键。

✗

写得越长越好。

✓

要的是“关键信息齐全”，不是字数多。简单的事一两句就够，复杂的事才需要完整的简报。

✗

它问我问题，说明它不够聪明。

✓

先问清楚会影响结果的空白，正是靠谱同事的做法。比起做完再返工，问一句省事得多。

08小测验

Q1下面哪一条是“可以检查”的完成标准？
C 做没做到一眼就能看出来，Claude 自己也能判断。A 和 B 没有明确的标准。
Q2“周六有雨，所以要室内的”比“要室内的”好在哪里？
知道“为什么”，Claude 就能把这个理由用到你没想到的地方。
Q3Claude 做到一半，你发现它理解错了一个条件。最好的做法是？
越早纠偏，浪费的步骤越少。它会根据你的新信息调整后面的做法。
Q4（开发者）“测试命令是 pnpm test”这条信息，最适合放在哪里？
每次都适用的约定写进 CLAUDE.md，每次会话自动加载；当次任务特有的目标和标准才写进简报。

09推荐工具与延伸

同一类简报反复用时，可以把它做成 Skill，让 Claude 记住这套固定流程（第 7 课）。官方示例库可以先看看别人是怎么写的。卡片上的“核实于”日期，是最后一次检查维护状态和许可证的时间。
